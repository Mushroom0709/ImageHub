# ADR 0017 — 实时进度推送方案

**状态：Amended** · 2026-08-08 · 修正于 2026-08-08

## 决策修正

原计划统一用 SSE 推送所有进度。实际实现后调整为：

### 用户上传进度 → XHR upload.onprogress（已实现）

上传阶段（文件传到 OBS）用前端 XHR 的 `upload.onprogress` 事件，原因：
1. **最精确**：浏览器原生支持，字节级进度，无延迟
2. **最简单**：不需要后端维护 SSE 连接和任务状态
3. **预签名直传**：前端直接传 OBS，后端不经过数据流，推不了 SSE
4. **并发 3 个文件**：前端维护上传队列和进度

后端处理阶段（缩略图/EXIF/AI打标）目前是同步完成的（complete 接口阻塞直到处理完），所以上传完成 ≈ 全部处理完成。未来如果改异步处理再加 SSE。

### 采集任务进度 → SSE（保留原方案）

小红书/抖音采集是后端发起的异步任务，必须用 SSE 推送进度：
- 抓取详情 → 下载图/视频 → 上传 OBS → 打标 → 入库
- 每一步都是后端在做，前端只能轮询或 SSE
- SSE 比轮询节省资源、实时性更好

## 进度数据结构（上传）

每个文件的状态流转：
```
waiting → uploading → processing → done
                              ↘ failed
```

前端展示（右下角浮动面板）：
- **顶部统计**：已完成/总数 + 总百分比
- **总进度条**：按字节汇总（已上传字节 / 总字节）
- **文件列表**：每个文件的状态图标 + 文件名 + 百分比/大小 + 单文件进度条

## 适用场景对照表

| 场景 | 实现方式 | 状态 |
|---|---|---|
| 用户上传进度 | XHR upload.onprogress | ✅ 已实现 |
| 小红书采集进度 | SSE | ✅ 已实现（采集任务流） |
| 抖音采集进度 | SSE | ✅ 已实现（复用采集任务流） |
| 后端 AI 打标进度 | — | 未做（目前同步阻塞，complete 返回即完成） |
| 批量导出进度 | SSE | 未做 |

## 为什么不全部用 SSE

- 预签名直传 OBS 的架构下，上传数据流不经过后端，后端没法推上传进度
- XHR 进度比 SSE 更实时、更简单、更可靠
- SSE 适合后端主导的异步任务（采集、导出、批量处理）
